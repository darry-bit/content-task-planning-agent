# 怎样形成真实、可展示的个人贡献

这是**可选后续学习指南**，不代表当前项目缺少题目要求的实现或验收。当前实际贡献与 AI 使用记录以 `04-ai-usage.md` 为准。

当前代码由 AI 辅助生成。目标不是修改几处变量名或删去 AI 痕迹，而是自己做一次完整的业务判断、实现和验证。下面的任务均尚未由用户完成，不能直接复制成自述。

## 第一步：亲自复现三个案例

照 README 运行正常、预算 10、估算失败案例。自己打开 output 和 Trace，计算并解释：

1. 为什么正常费用是 12.70，而不是 12？
2. 为什么调整后是 9.10，而不是 8？
3. 估算失败时为什么脚本版本仍为 1，账本里没有多一次生成费？

把你的解释写进个人记录。向 AI 提问可以记录为“AI 辅助理解”，但只有你实际运行与核对后才能写“我验证了”。

## 第二步：完成一个明确改进（推荐素材与渠道适配检查）

业务问题：现实素材不一定适合所有发布渠道，便宜素材若不支持 video，不能只看价格就选它。

建议练习：

1. 在合成规则的某个素材上添加 `allowed_channels`，例如只允许 post；先决定这是演示业务规则，并说明原因。
2. 在 `tests/test_tools.py` 写一个失败用例：使用该素材生成 video 脚本应返回明确错误，而不是成功。
3. 运行测试，确认初版暴露了缺少检查的问题；保存结果或真实提交。
4. 在 `tools.py` 的参数校验中实现规则，返回可供模型观察的稳定错误码，例如 ASSET_CHANNEL_MISMATCH。
5. 同时验证允许的 post 方案仍可生成；运行全部测试。
6. 更新合成数据说明、模型提示和验收预期。不要为了保留旧测试结论，暗中删掉原有失败用例。
7. 在真实模式中观察模型收到不匹配错误后是否改用其他素材或渠道。如果没有恢复，也要记录。

这次修改会改变规则指纹，旧检查点不能续跑，应使用新目录。改规则后离线总表可能变化，这是需要重新验收的正常结果。

可展示的贡献应包含：你定义的业务约束、你写或修改的测试、实现差异、实际运行结果和真实提交。若实现仍大量依赖 AI，也应准确说明你的设计、检查与验证角色。

## 第三步：记录可审查的前后变化

填写下面内容，引用实际文件和 commit：

- 问题触发输入：待填写。
- 修改前实际行为：待填写。
- 我作出的取舍：待填写。
- 我亲自完成与 AI 辅助部分：分别填写。
- 修改后行为和测试：待填写。
- 失败或局限：待填写。

不要把“准备做”写成“已完成”。当前 AI 初版的参数类型修复和续跑实现也不能当成你的手写经历。

## 第四步：准备能解释的演示

建议用约三分钟展示：任务输入与约束、一次正常运行、一次失败/预算反馈、当前费用账本、你的改进及对应测试。只有你能解释实现与失败边界的功能才应作为你的贡献重点。

可用的提问清单：如果保存失败会怎样？为什么不能拿旧估算保存新脚本？达到步数上限会返回什么？真实模型从未尝试昂贵方案时能否声称发生过预算重规划？API 费用是否包含在模拟单位中？

## 提交前核对

真实模型至少两条不同执行路径、至少三组覆盖全部必选点的材料、明确的 AI 使用记录、自己的实践证据、可复制命令、GitHub 可读性，以及题号 2 / 仓库 URL / 最终 commit SHA。尚未做到的项目应列为未完成。
